# 16: 响应 Cookie 在响应被接受后才并入并持久化

**Finding:** F6 · .scratch/weread-cron-v1/findings/01-implementation-review.md
**Category:** bug
**Blocked by:** None
**Status:** ready-for-agent

**What to build:** 公共 HTTP 响应路径先校验状态与业务成功、再并入并持久化响应 Set-Cookie；失败的 renewal 等响应不改写持久化 Login Session。

## Current behavior

公共 HTTP 响应处理在返回调用方前就合并响应 Set-Cookie（经会话层持久化），随后才校验 HTTP 状态、再交由调用方校验业务响应。对 renewal：收到响应 → 合并并持久化 Set-Cookie → 校验 HTTP 状态 → 解析校验 succ。一个未被接受的失败响应仍可能改变持久化的 Login Session，违反"失败的 renewal 让最后一次已知 Login Session 保持不变"的事务预期。

## Desired behavior

响应 Set-Cookie 只在响应被接受后（HTTP 状态与业务成功均通过）才并入并持久化。失败的 renewal 不改变持久化 Login Session。合并失败的报错语义保持。对其它请求路径（report / Reader / Shelf）的 Set-Cookie 采用一致语义：业务接受后才合并。

## Key interfaces

- 公共 HTTP 响应路径（weread 客户端）：把"合并响应 Cookie"从响应处理早期移到调用方确认接受之后（或提供显式"接受后合并"步骤）。
- 会话层合并 + 原子持久化的语义保持。
- 各业务调用方（renewal / report / Reader / Shelf）在成功判定后触发合并。

## Acceptance criteria

- [ ] renewal 失败（HTTP 非 200 或 succ != 1）时不改写持久化 Login Session
- [ ] renewal 成功时新 Cookie 照常并入并持久化（回归）
- [ ] report 失败响应不并入其 Set-Cookie
- [ ] 现有会话恢复/持久化测试全部保持通过
- [ ] 合并失败的报错行为不回归

## Out of scope

- 登录失效判别特征（`ErrLoginInvalid`）的调整
- 会话文件格式

## 验证记录

Review 输入 F6 已对当前代码确认：

- 公共 do() 路径顺序：读 body → 合并响应 Set-Cookie → 校验 HTTP 状态 → 返回；Renewal 在此基础上再解析 succ。失败响应（非 200 或 succ != 1）的 Set-Cookie 已被合并并持久化。
