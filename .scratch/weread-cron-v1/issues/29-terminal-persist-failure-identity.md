# 29: 终态持久化失败可使已最终失败的 Task 继续运行并翻转为 success

## Agent Brief

**Category:** bug
**Summary:** 恢复链耗尽形成最终失败决策后，若 failed 终态写盘失败，返回的错误丢失"不可继续恢复"的业务身份，外层将其判为暂时性失败并重新进入 timed report 路径；后续上报成功可把原本的最终失败翻转为 success。

**Current behavior:**
- 恢复链耗尽时 Task 已满足最终失败条件，finalization 随即把 `failed` 终态写入持久化。
- 若此次 terminal-state 写盘失败，finalization 返回的错误不再保留原本用于表示不可继续恢复的错误身份（`report.ErrRejected` 或 `weread.ErrLoginInvalid`）。
- 外层（timed report 循环）的错误判别（`errors.Is(err, report.ErrRejected) || errors.Is(err, weread.ErrLoginInvalid)`）随即失效，把它识别为普通暂时性失败，重新进入 timed report 路径。
- 确定性复现：① 恢复链耗尽；② Task 已应进入 `failed`；③ 写入 `failed` 终态失败；④ 外层继续执行 timed report；⑤ 后续上报被接受；⑥ 最终写入 `success` 终态；⑦ Task 返回 nil。
- 恢复链内 renewal 步骤的登录失效 finalization（`failLoginInvalid`）存在同一类路径：其终态写盘失败时同样丢失 `ErrLoginInvalid` 身份并被外层当作暂时性失败。
- 影响：一个已满足最终失败条件的 Task 可以仅因本地终态持久化失败而继续运行并最终记录为 success，破坏两个核心约束——恢复/失败预算有界、终态决策形成后不得因 finalization 持久化失败重新进入业务执行路径；本地存储故障被错误混入网络/上报恢复逻辑。

**Desired behavior:**
- 终态决策一旦形成（最终失败），Task 绝不得重新进入上报业务路径，无论 finalization 持久化是否成功。
- 终态持久化失败时沿用既有语义（ticket 15 / #24）：不发最终通知、Task 返回持久化错误；但不得继续上报、不得在存储恢复后写入 success 终态。
- 返回的错误应保留终态决策身份（如包装持久化错误并同时保持 `ErrRejected` / `ErrLoginInvalid` 的判别身份，或以等价方式保证外围循环不会重入），使调用方能够区分"已形成终态决策但存储失败"与"可重试的暂时性失败"。
- 全部经恢复链回流入循环的终态决策出口（恢复链耗尽、链内登录失效）遵守同一规则。

**Key interfaces:**
- 终态 finalization 出口（`failRecoveryExhausted`、链内登录失效 finalization）及其错误向 timed report 循环的传播：循环在任何终态决策点之后都不得重入。
- `finalize` 的持久化失败路径：保留终态决策的错误身份（包装或重构，使重入不可能）。
- 相关注释同步（现注释声称错误身份"包装链保留、errors.Is 贯通"，终态写盘失败时该保证不成立）。

**Acceptance criteria:**
- [ ] 按 findings/07 H4 的确定性复现（恢复链耗尽 → 首次 failed 写盘失败 → 存储恢复 → 后续上报可被接受）运行，Task 仍以失败终止：不写 success 终态、不发成功通知、决策点之后不再继续上报。
- [ ] 返回的错误指明终态持久化/存储失败，且不被调用方判为"可重试的暂时性上报失败"。
- [ ] 恢复链内登录失效 finalization 的终态写盘失败遵守同一规则（不重入、不翻转为 success）。
- [ ] 既有"持续写盘失败"测试回归：不发任何通知、Task 返回错误（`TestRunTerminalPersistFailureSuppressesNotification`）。
