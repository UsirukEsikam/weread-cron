# 21: GHCR `latest` tag semantics

**Finding:** F5 · .scratch/weread-cron-v1/findings/02-deployment-and-operations.md
**Category:** bug
**Blocked by:** None
**Status:** ready-for-agent

**What to build:** 修正 release.yml 的 metadata-action 配置，使 `latest` 标签的实际行为与项目既定发布模型一致:main 分支 → `latest`（+ `main`）;`v*` tag → 仅版本标签（如 `v1.0.0`），不触碰 `latest`。

## Current behavior

release.yml 的 `docker/metadata-action@v5` step 未配置 `flavor`，tags 为:

- `type=ref,event=branch`（main → `main`）
- `type=ref,event=tag`（v* → 版本标签）
- `type=raw,value=latest,enable=${{ github.ref == 'refs/heads/main' }}`（latest 仅 main）

docker/metadata-action v5 的 `flavor.latest` 默认 `auto`:对 `type=ref,event=tag`（semver 形态的 git tag）会**自动附加** `latest`。因此推 `v*` tag 时实际发布 `v1.0.0, latest`，latest 被版本构建意外更新，与文件头注释「main 分支推送 → latest;v* 版本 tag → 版本标签」的模型相矛盾。这是文档化模型与实际发布行为的差异。

## Desired behavior

- main 分支推送:`latest` + `main`（不变）
- `v*` tag 推送:仅版本标签（如 `v1.0.0`），**不含** `latest`
- 实现方式建议:metadata-action 增加 `flavor: latest=false`（或等价地禁用 flavor 的 auto-latest），保留现有显式 `type=raw,value=latest,enable=main` 负责产生 latest
- 注释/README 中「latest = main 分支镜像」的发布模型保持不变，本轮只对齐实现

## Key interfaces

- `.github/workflows/release.yml`:metadata-action step 的 `tags` 与新增 `flavor` 输入;文件头注释
- README「镜像」章节对发布策略的表述（若需与实现一致化）

## Acceptance criteria

- [ ] `v*` tag 构建产出的 tags 不含 `latest`（metadata-action dry-run 或等价方式验证）
- [ ] main 构建仍产出 `latest` 与 `main`
- [ ] release.yml 注释与 README 所述发布模型与实际行为一致

## Out of scope

- 改变「latest = main 分支镜像」的发布模型本身（模型既定，本轮只对齐实现）
- release.yml 其它配置（权限、平台、缓存、镜像路径——镜像路径属 ticket 20 的 F4）

## 验证记录

一手来源（docker/metadata-action v5 README）: `flavor` 输入 `latest` 默认 `auto`，对 `type=ref,event=tag`、`type=semver`、`type=pep440`、`type=match` 默认生成 `latest`;表格示例 `push tag v1.2.3 → v1.2.3, latest`。

当前 release.yml 未设置 `flavor`，且显式 `type=raw,value=latest,enable=main` 表达「latest=main-only」意图，两者叠加后 `v*` tag 构建会同时带 `latest`——F5 属实。
