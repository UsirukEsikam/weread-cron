# 15: failed 终态持久化是失败通知的严格前置（终态先落盘再通知）

**Finding:** F5 · .scratch/weread-cron-v1/findings/01-implementation-review.md
**Category:** bug
**Blocked by:** None
**Status:** ready-for-agent

**What to build:** 失败路径与成功路径一致：failed 终态持久化是发送失败通知的严格前置。

## Current behavior

成功路径：终态持久化失败 → Task 报错返回，不发成功通知。失败路径（恢复链耗尽、登录失效、自动选书失败）：先尝试写 failed 终态，写入失败只记日志，仍继续发送失败通知。若持久化失败，用户收到最终失败通知，而持久化状态没有当日结果；后续 daemon 执行看到无终态，会再次尝试运行当天 Task——与已通知的"最终失败"矛盾。

## Desired behavior

失败路径与成功路径一致：failed 终态持久化是发送失败通知的严格前置。持久化失败时不发送失败通知（该次失败按未收敛处理：返回持久化错误，由调度层决定重排；不发出"已终结"的失败通知）。保证"已发送的失败通知 ↔ 持久化中存在对应 failed 终态"。

## Key interfaces

- Task 失败收敛的三个出口（恢复链耗尽、登录失效、自动选书失败）：将 failed 终态持久化失败从"记日志继续"改为"返回错误、不发通知"。
- 成功路径行为保持（终态先落盘再通知，持久化失败即报错）。
- 通知失败不影响 Task 结果与终态的现有语义（用户故事 #38）保持——本票只改"终态持久化失败"的处理。

## Acceptance criteria

- [ ] 三个失败出口在 Terminal Save 失败时不发送失败通知
- [ ] Terminal Save 成功时失败通知正常发送（回归）
- [ ] 成功路径持久化失败行为不变
- [ ] 通知发送失败不影响终态的语义保持（回归）
- [ ] 不存在"已发送失败通知但持久化无当日终态"的可达状态

## Out of scope

- 成功通知的时序
- 通知渠道的凭据脱敏（F9/ticket 19）
- 暂时性失败收敛（F2/ticket 12）
