# 11: 同一 deployment 内 daemon 与 run 的跨进程 Task 互斥

**Finding:** F1 · .scratch/weread-cron-v1/findings/01-implementation-review.md
**Category:** bug
**Blocked by:** None
**Status:** ready-for-agent

**What to build:** 同一 deployment（同一 /data）内 daemon 与 `weread-cron run` 的跨进程 Task 互斥：已有 Task 运行时第二个 Task（自动或手动）被拒绝。

## Current behavior

Task 并发守卫是进程内 `sync.Mutex`（TryLock 非阻塞拒绝，返回 `ErrTaskRunning`）。CLI 每次命令调用都新建一个应用实例，各自持有独立的 mutex；Docker `docker compose exec weread-cron /weread-cron run` 是另一个操作系统进程。Task 运行期间不落终态，故第二个进程同样通过终态门控并启动第二个 Task。当前没有任何跨进程互斥机制。

## Desired behavior

同一 deployment（同一 /data 目录）内，已有 Task 运行时第二个 Task（自动或手动）被拒绝，保持 `ErrTaskRunning` 语义（非阻塞拒绝、不等待、不中断运行中的 Task）。锁在进程退出（含崩溃）后自动释放，不会永久卡死。范围限定单机同一 /data；不同 deployment（不同 /data）互不干扰。

## Key interfaces

- `App.RunTask` 的并发守卫：从"进程内互斥"升级为"同一 deployment 内跨进程互斥"，保持 TryLock 的非阻塞拒绝语义与 `ErrTaskRunning` 错误判别。
- `App.ListBooks`：与 Task 共用同一互斥（运行中返回 `ErrTaskRunning`，避免与运行中 Task 的会话写竞争）。
- 互斥载体：建议基于 /data 下的锁文件 + 内核自动释放机制（进程退出/崩溃时由内核释放）。实现取舍需在实施时说明。

## Acceptance criteria

- [ ] daemon Task 运行中，另一进程执行 `weread-cron run` 被拒绝（`ErrTaskRunning` 语义、非阻塞）
- [ ] `run` 运行时，daemon 到点不启动第二个 Task
- [ ] 锁持有进程正常退出/崩溃后，后续 Task 可正常执行（锁自动释放）
- [ ] 同一进程内多协程并发 RunTask 仍被拒绝（进程内守卫回归）
- [ ] 不同 /data（不同 deployment）互不互斥（范围边界保持）
- [ ] 拒绝路径不中断运行中的 Task

## Out of scope

- 分布式/多实例（跨主机的多 deployment）协调
- `run --force` 或任何绕过互斥的选项
- 改变"Task 运行中不落终态"的时序（那是 F2/ticket 12 的范畴）

## 验证记录

Review 输入 F1 已对当前代码确认：

- 进程内 `runMu sync.Mutex` + `TryLock` 非阻塞拒绝（internal/app/app.go；`ErrTaskRunning` 判别）；终态门控在锁内，终态仅在 Task 结束后落盘，故第二个进程也通过终态门。
- CLI 每次命令调用都新建 App（internal/cli 的 `prodApp` → `app.New`）；daemon 与 run 是独立进程、独立 mutex。
- 代码库无 flock / O_EXCL / 锁文件等跨进程机制。
- spec 决策 #11 的"多实例防重不在 V1 范围"指不同 deployment/instance 的协调；同一 deployment 内 daemon 与正式支持的 run 入口互斥属于 V1 要求（用户故事 #43）。本次为修复该实现缺口，不扩展为多实例协调。
