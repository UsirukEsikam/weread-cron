## Agent Brief

**Category:** bug
**Summary:** Reader Context 一旦被成功采用，使用该 Context 发送任何 timed report 之前必须先成功 enter——TTL 到期主动刷新与恢复链内 refresh 同规则。当前实现刷新 Context 后直接继续 timed report，长会话在首个 TTL 边界（≈15 分钟）确定性失败。

**Current behavior:**
- **TTL 主动刷新**：timed report 循环每笔上报前经 `Reader.Fetch` 取 Context——TTL（`DefaultContextTTL`，参考默认 ≈15 分钟）内命中缓存零网络请求；到期时重新抓取 Reader 页刷新 Context（新 token/psvts），随后直接发送该笔 timed report，不 enter、不中断。
- **恢复链 refresh**：`recoverSend` 的 step 0/3 仅强制重新抓取并替换 Reader Context；retry 步骤复用调用方传入的发送闭包——timed 循环里该闭包是 `Sender.Timed`，不是 enter report。链中任何一步都不会重新 enter。
- **唯一 re-enter 触发点**：异常墙钟间隔超过 `DefaultAnomalyThreshold` 时的重建分支（重新 enter；ADR-0004）。
- **实证（checklist #7/#8，2026-09-06 晚间会话）**：issue 30 修复后，20 分钟 manual Task 持续被接受至 19:51:56（≈Task 开始 15 分钟 = TTL 边界）；TTL 到期刷新 Context 后的首笔 timed report 被服务器以空对象拒收；恢复链 refresh → retry → renewal → refresh → retry 全为 timed、全部被拒，恢复链耗尽、failed 终态——长会话在首个 TTL 边界确定性失败。
- **对照参考行为**：官方 Web Reader 重建页面上下文后重新 enter（新页面会话以 enter report 开始）；weread.koplugin 每次 Context 重建（TTL 到期或强制刷新）清除 entered 状态，随后的发送先发 enter report 再发 timed report。

**Desired behavior:**

统一不变量：任何新的 Reader Context 一旦被成功采用，在使用该 Context 发送任何 timed report 之前，必须先成功 enter。该规则同时适用于：

1. TTL 到期主动刷新（timed 循环每笔前的 Fetch 发现 TTL 过期、重新抓取获得新 Context）；
2. 恢复链内 refresh Reader Context（step 0/3 的强制刷新）。

语义细节（生命周期与边界）：

- **新 Context + re-enter 视为新的协议 Reading Session**。若 `pclts` 缺失或为 `"0"`，在 re-enter 时重新生成一次 fallback pc（值 = `e(会话建立时刻的秒级时间戳)`），并在该 Session 内保持稳定——与 issue 30 生命周期规则一致：明确重新 enter = 新会话 = 新会话级 pc；同一会话内的 refresh 不改变 pc。可用 `pclts`（非空、非 `"0"`，ticket 25 语义）场景 pc 继续来自 Reader Context，re-enter 后取新 Context 的值。
- **re-enter 成功不得清零 consecutive timed-report failure budget**；仍只有被接受的 timed report 才能清零（issue 27 语义保持——re-enter 只证明 Reading Session 重建，不证明 timed report 路径已恢复）。
- **re-enter 后重新建立 rt interval 起点**：不把旧 Session 的长间隔带入下一笔 timed report；re-enter 的 enter 被接受后，rt 基准从其被接受时刻重置（ADR-0004 既有语义）。任何一笔 timed report 的 `rt` 均不超过 `DefaultAnomalyThreshold`。
- 实现方式（TTL 主动刷新路径先行 enter、或恢复链 refresh 后先 enter 再 retry、或统一在「Context 变更」处重入）由实施代理自行选择，以行为验收为准，不预先锁定签名形态。

**Key interfaces:**
- `internal/task` 的 timed report 循环（每笔前的 `Reader.Fetch` 主动刷新点）与 `recoverSend`（恢复链 step 0/3 的 refresh、retry 闭包）：「Context 被成功采用后、任何 timed report 之前必须 enter」的判定与发送点。
- `sendEnter`（会话建立与 re-enter 共用入口）：re-enter 时解析新的会话级 pc（fallback = `e(会话建立时刻)`），天然承担「新 Session 新 pc」职责；被拒时经恢复链恢复。
- `report.Sender.Enter` / `report.Sender.Timed`、`weread.ResolvePC`（issue 30）：pc 生命周期语义复用，不另造机制。

**Acceptance criteria:**
- [ ] TTL 到期主动刷新后（Fetch 返回重新抓取的新 Context），下一笔上报是 enter report；enter 被接受后才继续 timed report；后续 timed report 全部被接受。20 分钟 Task 跨 TTL 边界持续成功（enter 数 = 2：初始 + TTL 边界；边界前 timed 使用初始 Context、边界后 timed 使用新 Context）。
- [ ] 恢复链内 refresh Reader Context 后，下一次上报是 enter report（非 timed retry）；enter 被接受后才继续 timed report。典型路径：timed 被拒 → refresh → enter（新 Session）→ timed 恢复成功。
- [ ] re-enter（TTL 边界或恢复链 refresh 后）生成新的会话级 fallback pc（`pclts` 缺失/`"0"` 场景），该新 Session 的 enter 与全部 timed reports 复用该 pc，不复用前一会话的值；可用 `pclts` 场景 re-enter 后 pc 取新 Context 原值（issue 30 生命周期规则）。
- [ ] re-enter 成功不清零 consecutive timed-report failure budget：仅被接受的 timed report 清零（issue 27 语义回归：慢失败收敛为 failed 终态 + 重建 enter 不清零的测试保持通过）。
- [ ] re-enter 后 `rt` 从新 enter 被接受时刻起算，旧 Session 的长间隔不作为一笔大 `rt` 上报（ADR-0004；所有被发送 timed report 的 `rt` 均 ≤ `DefaultAnomalyThreshold`）。
