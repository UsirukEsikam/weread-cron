# 12: 暂时性失败需收敛为 failed 终态与失败通知（当天不静默空过）

**Finding:** F2 · .scratch/weread-cron-v1/findings/01-implementation-review.md
**Category:** bug
**Blocked by:** None
**Status:** ready-for-agent

**What to build:** 自动 Task 的最终失败（窗口内无法再重排）必须形成 failed 终态并发失败通知；timed report 的传输级失败不再无条件立即终止整个 Task。

## Current behavior

- Task 中 renew / 选书 / Reader 抓取 / enter / timed report 的传输级失败（传输错误、HTTP 非 200、解析失败）直接返回错误：不写终态、不发通知。
- daemon 收到该错误视为暂时性失败，窗口内重排；窗口已过则直接排次日。结果：当天可能"无 success 终态、无 failed 终态、无再次尝试、无失败通知"。
- timed report 的传输级失败（非明确拒绝）会立即终止整个 Task 尝试，即使剩余目标时长充足。

## Desired behavior

- 自动 Task 的最终失败必须形成 failed 终态并发失败通知（含失败阶段、主要错误、已尝试恢复动作），不允许静默空过一天。
- 窗口内重排语义保留：暂时性失败可再次调度；但当窗口耗尽且当天仍无终态时，最后一次失败收敛为 failed 终态 + 通知。
- timed report 的传输级失败不应无条件立即终止 Task：按暂时性处理（可在会话内重试/继续累计，或最终按失败收敛），不因一次抖动丢失整个 Task。

## Key interfaces

- Task 编排层各失败返回路径与 daemon 调度层的交互：需要一个"暂时性失败可重排"与"最终失败必收敛"的边界。
- 失败通知（notify 的 Failure 形态）已含失败阶段/主要错误/已尝试恢复动作，复用即可。
- 与 spec 决策 #7 的暂时性失败姿态（不写终态、当日可再次调度）调和：收敛只发生在"无法再调度 / 窗口耗尽"时。

## Acceptance criteria

- [ ] 窗口末尾发生的暂时性失败最终形成 failed 终态并发送失败通知（当天不再静默空过）
- [ ] 窗口内有剩余时间时，暂时性失败仍按现有语义重排（回归）
- [ ] timed report 单次传输失败不再立即终止整个 Task（恢复/继续，或按失败收敛，视修复方案）
- [ ] 失败通知包含失败阶段、主要错误、已尝试恢复动作
- [ ] failed 终态落盘后 `weread-cron run` 可手动重试（现有行为回归）

## Out of scope

- 成功路径的改动
- 分布式/多实例协调
- 失败通知的凭据脱敏（那是 F9/ticket 19 的范畴）

## 验证记录

Review 输入 F2 已对当前代码确认：

- Task 编排层所有暂时性失败路径直接返回错误（不写终态、不通知）；仅三处写终态 + 通知：恢复链耗尽、登录失效、自动选书无可用书。
- daemon 收到 Task 错误 → 日志 + 最短重排间隔后重排；`NextStart` 窗口已过 → 排次日。窗口耗尽时当天无终态、无通知。
- timed report 循环中恢复链返回非"明确拒绝"错误时立即返回并终止整个 Task。
