# Fallback `pc` Should Be Stable Within a Reading Session

> *This was generated by AI during triage.*

**Status:** tracked

**Tracking:** 本 finding 依据 ticket 23 受控真实验证记录整理，证据存于 `docs/protocol-validation-checklist.md`（2026-09-06 会话记录与官方 Web Reader 抓包记录）。已由 triage 独立建票为 `.scratch/weread-cron-v1/issues/30-reader-pc-session-stable-fallback.md`（bug，ready-for-agent）。fallback `pc` 生命周期口径已定：`pclts` 缺失或为 `0` 时在新的 Reading Session 建立时生成一次 fallback `pc`，该会话的 enter 与全部 timed reports 复用；仅明确建立新的 Reading Session 时重新生成；单纯 Reader Context refresh 不因本票改变 `pc`；本票不决定 TTL refresh 或 `-2012` recovery 是否 re-enter。真实账号端到端长跑确认继续由 ticket 23 / checklist 跟踪——本 finding 在实施并经一次完整的成功长跑确认前不标 resolved；issue 30 关闭不以此为前置（修复 + 相应测试通过即可）。

## Context

Real-account validation under ticket 23 produced the following recorded evidence:

1. Real Reader state can return `reader.pclts` as the JSON number `0`.
2. Manual testing without a fixed `pc` showed that the real service rejected long Tasks with an empty-object response after about 5–5.5 minutes. The failure was reproducible:
   - on a previously read book, a newly added unread book, and a completed book;
   - after recreating the container/volume and supplying a fresh initial Cookie.
3. The current implementation regenerates the fallback `pc` on every report payload construction. In `internal/weread/protocol.go`, the shared payload builder computes `pc = EncodeID(now)` each time when `pclts` is empty or `"0"`. Both `EnterReportPayload` and `TimedReportPayload` use this builder. In the `pclts == 0` scenario, every report inside one Reading Session therefore carries a different `pc`.
4. Official Web Reader capture: for a Reader page whose initial `pclts` was numeric `0`, the official client sent a non-zero `pc` and reused that same value across the enter report, consecutive timed reports, and real page turns within one page session. `pc` and `ps` remained stable while `ct`, `rt`, `rn`, `sg`, `s`, and reading-position fields changed as expected.
5. Real-account probe: with the fallback `pc` temporarily fixed for the lifetime of one Reading Session, Timed reports remained accepted beyond the previous ~5–5.5 minute failure point and continued successfully for about 7 minutes.

## Finding

Problem fact:

When Reader Context yields no usable `pclts` (empty or `"0"`, as observed with real numeric `0`), weread-cron sends a new fallback `pc` on every report payload, while the official client keeps `pc` stable within one page session. The evidence links the unstable fallback `pc` to the empirical ~5–5.5 minute rejection point: fixing `pc` for one Reading Session crossed that point.

Expected behavior:

When Reader Context yields no usable `pclts`, the fallback `pc` must be established once per Reading Session and reused by all reports of that session — the enter report and every Timed report — consistent with the official client behavior and the real-account probe result.

Evidence status: the validation record states that session-stable fallback `pc` is strongly supported by real-account evidence but still requires one complete successful long run before it is treated as fully confirmed. This finding records the behavior expectation; it does not claim that an unstable `pc` is the proven single cause of the long-session rejection.

## Scope boundary

- This finding covers only the fallback `pc` behavior when real Reader state has no usable `pclts` (observed: JSON number `0`).
- It does not change behavior when Reader Context supplies a usable `pclts`; in that case `pc` continues to come from Reader Context.
- It does not establish the implementation approach. Where the session-stable value is stored, when it is generated, how session identity is defined, and whether Reader Context refresh or re-enter restarts it are left to triage and the affected implementation ticket.
- It does not resolve:
  - the `-2012`（登录超时）response at about 7.5 minutes and whether it means Login Session expiry or Reading Session expiry;
  - the recovery-chain behavior after `-2012`（refresh / retry / renewal retries rejected with empty-object responses);
  - whether Reader Context refresh requires re-enter（checklist #7）;
  - Reader Context TTL（checklist #8）;
  - `rt` interval semantics（checklist #11 / ADR-0004）;
  - independent validation of unread and completed books（blocked by the long-session rejection and still unvalidated）.
- Parsing compatibility for numeric `pclts` is out of scope here; it is already resolved under ticket 25.
