## Context

Post-implementation review exposed several edge cases around transient Task failures, Run Window exhaustion, restart behavior, manual `run`, and Terminal State dates.

Further product discussion clarified the intended boundary between:

- normal daily scheduling;
- abnormal daemon startup or restart;
- recovery inside an active Task;
- completion of a Task;
- manual `run`.

The normal daily scheduling requirement has not changed:

> A continuously running daemon chooses one random start time inside the configured Run Window.

The clarification concerns abnormal recovery and Task completion semantics.

## Finding

The current implementation allows some completed Task invocations to return without a Terminal State so that the scheduler can start another complete Task later in the same Run Window.

This makes the scheduler responsible for both scheduling and whole-Task retry policy.

It also requires Task execution to know whether another scheduling opportunity remains.

The resulting behavior is more complex than the intended product model and creates inconsistent finalization semantics.

## Intended scheduling semantics

### Normal daily scheduling

For a continuously running daemon with no Terminal State for the day:

- before the Run Window, choose one random start time inside the complete Run Window;
- wait until that start time;
- start the Task.

Random daily scheduling remains part of the V1 product behavior.

### Abnormal daemon startup or restart

When the daemon starts or restarts and the current day has no Terminal State:

- if current time is before the Run Window, schedule the normal random start for that day;
- if current time is already inside the Run Window, start the Task immediately;
- if current time is after the Run Window, do not run an automatic Task for that day.

The immediate start inside the Run Window applies only to abnormal startup or recovery.

It does not change normal daily random scheduling.

### Process interruption

If the process exits or crashes during a Task before a Terminal State can be written, the next daemon startup follows the abnormal startup rules above.

No Task checkpoint or precise Task resume is required.

A fresh Task can therefore start immediately when the daemon recovers inside the remaining Run Window.

## Intended Task semantics

Once a Task starts, the Run Window no longer controls that Task.

The Task can continue beyond the Run Window and can cross midnight.

Temporary network or protocol problems are handled through bounded recovery inside the active Task.

After bounded recovery is exhausted, the Task has reached a final result.

A normally completed Task invocation has one of two results:

- `success`;
- `failed`.

Both results produce the corresponding Terminal State.

A final failure also produces the configured failure notification after the Terminal State has been persisted successfully.

An automatic Task that reaches `failed` is not automatically replaced by another complete Task later in the same Run Window.

Manual recovery remains available through `weread-cron run`.

## Manual `run`

`weread-cron run` continues to ignore the Run Window and starts immediately when the existing Terminal State rules allow it.

The Task execution semantics are otherwise the same as an automatic Task:

- bounded recovery occurs inside the Task;
- success produces a success Terminal State;
- final failure produces a failed Terminal State and failure notification.

A failed Terminal State continues to permit another manual `run` after the user has corrected the underlying problem.

## Task date

A Task belongs to the day for which it was started.

That Task date is established when the Task starts and remains stable for all final results.

For example:

    Run Window day: 2026-09-05
    Task starts:    2026-09-05 23:50
    Task finishes:  2026-09-06 00:40

The resulting Terminal State belongs to `2026-09-05`.

Crossing midnight does not transfer the Task to the next day's scheduling state.

The same Task-date rule applies to success and all final failure paths.

## Current implementation conflict

The current post-review implementation contains behavior that does not match the clarified model.

In particular:

- a transient Task failure can return without a Terminal State so that the daemon can schedule another complete Task in the same Run Window;
- scheduler retry timing participates in deciding whether a Task failure is final;
- Task execution receives a final-failure deadline derived from the remaining scheduling window;
- different failure paths can have different finalization behavior;
- manual `run` has different transient-failure finalization behavior from an automatic Task;
- some Terminal State paths derive their date from completion time rather than one stable Task date.

The implementation therefore mixes scheduling policy with Task failure finalization.

## Scope boundary

This finding does not change:

- the normal random start inside the Run Window;
- Target Duration randomization;
- bounded recovery inside an active Task;
- Reader Context or Reading Session recovery behavior;
- the rule that a Task may continue after the Run Window ends;
- the rule that missed days are not backfilled;
- the ability to retry a failed day manually with `weread-cron run`;
- the existing distinction between a process crash with no Terminal State and a normally completed Task.

This finding concerns only the boundary between scheduler recovery, whole-Task retry behavior, Task finalization, and Task-date ownership.
