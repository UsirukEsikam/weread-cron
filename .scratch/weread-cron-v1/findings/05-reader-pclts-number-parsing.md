# Reader `pclts` Numeric Value Is Rejected

**Status:** resolved

> *This was generated by AI during triage.*

**Tracking:** 本 finding 已由 triage 独立建票为 `.scratch/weread-cron-v1/issues/25-reader-pclts-numeric-parsing.md` 并实施完成（resolved）。协议实机验证总项仍由 ticket 23 主跟踪。

## Context

Controlled real-account validation under ticket 23 reached the Reader Context stage.

The real Reader page returned:

    "psvts":"5cb328e07aa94b32g0140f1",
    "pclts":0

`psvts` was a JSON string.

`pclts` was a JSON number with value `0`.

The validation evidence is recorded in `docs/protocol-validation-checklist.md`.

## Finding

The current Reader state parser defines `reader.pclts` as a string.

Parsing the real `__INITIAL_STATE__` therefore fails before Reader Context can be established:

    json: cannot unmarshal number into Go struct field InitialState.reader.pclts of type string

This prevents both explicit-book and automatic-book Tasks from progressing past Reader Context when the real Reader state contains numeric `pclts`.

The existing protocol behavior already treats an absent or zero `pclts` as the condition for the current `pc` fallback.

The observed real value is numeric zero, so the validation result does not establish a new `pc` protocol semantic. It establishes a parser compatibility requirement: the Reader state parser must accept the observed numeric representation without changing the existing zero-value fallback behavior.

## Scope boundary

This finding is limited to the observed `reader.pclts` representation.

It does not establish that other Reader state fields require generalized mixed-type parsing.

It does not change the existing `pc` fallback semantics.

It does not resolve other protocol-validation items tracked by ticket 23.
