## High

### H1. Recovery enter can reset the failure budget and prevent a Task from converging

**类型：** implementation defect

**位置：**
- `internal/task/task.go:342–389`

**事实：**
Timed report 连续失败达到恢复条件后，Task 会重新建立 Reader Context / Reading Session，并再次执行 `enter`。

当前实现只要重新 `enter` 成功，就会清零 `consecutiveFailures`。

但 `enter` 成功只能证明阅读上下文重新建立成功，不能证明后续 Timed report 已经恢复正常。

确定性复现中，每次 Timed report 均在约 20 秒后失败，随后 Context 刷新和重新 `enter` 也会消耗时间。结果出现：

- 8 次 Timed report 失败；
- 4 次重新 `enter`；
- 每次 `enter` 成功后失败计数被清零；
- Task 始终没有进入最终失败状态，只能通过主动取消结束。

**影响：**
持续故障时，Task 可以反复通过重新 `enter` 重置失败预算，失去“有界失败后必须收敛”的保证。

长期运行的 Task 会持续占用 task lock，从而阻止：

- manual run；
- `books`；
- 后续自动 Task。

**测试遗漏：**
现有 failure-budget 测试中的失败响应基本不会明显推进时间，没有覆盖：

`Timed report 慢失败 → 异常间隔 → 重建 Reading Session → 再次失败`

这一组合路径。


### H2. Recovery retries can report a large elapsed-time gap without rechecking continuity

**类型：** implementation defect

**位置：**
- `internal/task/task.go:320–364`
- `internal/task/task.go:520–526`

**事实：**
当前实现会检查两次上报之间的时间间隔。超过连续性阈值时，应认为 Reading Session 已经中断，不把这段大时间缺口计入阅读时长，而是重新建立 Reading Session。

但这个检查只发生在进入 recovery chain 之前。

进入 recovery chain 后，重试会重新计算 `rt`，却不会再次检查时间间隔是否已经超过阈值。

因此，如果恢复过程本身耗时较长，新的 `rt` 可以包含整个恢复期间的时间。

确定性复现中，恢复期间发生时间跳变后，程序实际发送了：

`rt=130`

一个目标时长只有 1 分钟的 Task 因此直接按累计 130 秒完成。

**影响：**
这违反 ADR-0004 已确定的连续性规则：

大时间缺口不应计入阅读时长；连续性中断后应重新建立 Reading Session。

因此当前实现可能把恢复过程中的非阅读时间作为阅读时长上报并计入本地累计。

**相关边界：**
该 finding 证明的是实现不符合项目自身已经确定的连续性规则。

它不用于断言微信读书服务端一定接受或拒绝这种较大的 `rt`；服务端协议行为仍属于真实账号验证范围。

另外，正常路径中的时间基准也可能在阻塞式 `Reader.Fetch` 前取得，因此恢复以外的阻塞耗时同样需要遵守相同的连续性边界。


### H4. Failure to persist a terminal state can allow an already-failed Task to continue and succeed

**类型：** implementation defect

**位置：**
- `internal/task/task.go:367–389`
- `internal/task/task.go:649–661`

**事实：**
当 recovery chain 已经耗尽时，Task 已经满足最终失败条件，接下来会通过 finalization 将 `failed` terminal state 写入持久化状态。

如果这次 terminal-state 写盘失败，当前返回的错误不再保留原本用于表示不可继续恢复的错误身份。

外层因此把它识别为普通的暂时性失败，并重新进入 Timed report 重试路径。

确定性复现中出现了以下过程：

1. recovery chain 耗尽；
2. Task 已应进入 `failed`；
3. 写入 `failed` terminal state 失败；
4. 外层继续执行 Timed report；
5. 后续上报成功；
6. 最终写入 `success`；
7. Task 返回 `nil`。

**影响：**
一个已经满足最终失败条件的 Task，可以仅因为本地 terminal-state 持久化失败而继续运行，并最终被记录为成功。

这破坏了两个核心约束：

- recovery / failure budget 必须有界；
- terminal decision 一旦形成，不应因为 finalization 持久化失败而重新进入业务执行路径。

同时，本地存储故障被错误混入网络/上报恢复逻辑，使“业务是否还能继续”和“终态能否成功写盘”两个不同问题发生混淆。

**测试遗漏：**
现有持久化失败测试主要覆盖“写盘持续失败”的情况，只验证最终返回错误以及不发送通知。

没有覆盖更关键的边界：

首次 terminal finalization 已经失败后，Task 不得重新进入 Timed report，并在后续成功后把原本的最终失败翻转为 `success`。
