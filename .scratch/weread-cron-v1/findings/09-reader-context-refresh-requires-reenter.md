## Current behavior（当前行为，源码对照）

`internal/task/task.go` 的 timed report 循环与恢复链现状：

- **TTL 主动刷新**：每笔 timed report 前经 `Reader.Fetch` 取 Context——TTL（15 分钟）内命中缓存零网络请求；到期时重新抓取 Reader 页刷新 Context（新 token/psvts）。刷新不重置 rt 基准：Reading Session 继续、无 enter、不中断；issue 30 后会话级 `pc` 亦不改变。
- **恢复链（`recoverSend`）**：step 0/3 的 refresh 仅强制重新抓取并替换 Reader Context；retry 步骤复用调用方传入的发送闭包——timed 循环里该闭包是 `Sender.Timed`，不是 enter report。链中任何一步都不会重新 enter。
- **re-enter 唯一触发点**：异常墙钟间隔超过 `DefaultAnomalyThreshold`（ADR-0004）时重建 Reading Session（重新 enter）。TTL 主动刷新与恢复链 refresh 均不触发 re-enter。
- **后果**：长会话必然跨越至少一次 TTL 边界；刷新 Context 后首笔 timed report 被拒；恢复链无任何步骤 re-enter，无法恢复；Task 在首个 TTL 边界处确定性失败。

## Expected invariants（预期不变量）

以下为行为级不变量，不预先锁定具体实现方式：

1. **Context 重建后必须 re-enter**：任何一次 Reader Context 重建（TTL 到期主动刷新 或 恢复链内 refresh）之后，服务端接受的下一笔上报必须是 enter report；timed reports 只能在重新 enter 之后继续。任何"刷新 Context 后直接继续 timed report"的路径与真实服务不兼容（已实证）。
2. **恢复链可恢复**：当拒收由"Context 变更需 re-enter"引起时，恢复路径必须包含重新 enter，使 Task 能越过 TTL 边界继续，而非在约 15 分钟处确定性失败。
3. **issue 30 的会话级 `pc` 稳定不变量保持**：re-enter（明确建立新的 Reading Session）生成新的会话级 `pc`（fallback 场景 = `e(会话建立时刻)`）；同一会话内的 refresh 不改变 `pc`。
4. **ADR-0004 的 `rt` 语义保持**：re-enter 不把大缺口作为一笔 `rt` 上报；重建后的 enter 被接受后，rt 基准从其被接受时刻重置（既有语义）。
5. **有界收敛保持**：新增的 re-enter 恢复路径不得破坏连续失败预算与有界恢复链的收敛保证（spec 决策 #7/#9/#12；ticket 27 的"重建 enter 不清零、仅被接受的 timed report 清零"预算语义不因本 finding 改变）。
